# Phone-supplied watch library

The phone publishes metadata for its Apple Watch playlist selection after a successful library load. Selected leaf playlists keep their order and ancestor folders; shared tracks appear once. Music and artwork identities are stored with the accepted snapshot for the file delivery service. Cached music and artwork are delivered automatically; files missing from the phone wait for a normal phone library sync.

The publisher reads the phone database in one operation, including local track edits. A saved source identity binds that database to the phone server URL and the JWT username. The identity is a SHA-256 namespace, not an authentication credential. Changing token signatures or expiries does not change it. Existing phone stores without source ownership request a full metadata refresh on their next sync before publishing, so saved data from a previous account cannot become a new account's snapshot.

When an authoritative phone library no longer contains a selected playlist, publication removes that ID and persists the surviving selection in the phone settings. Deleting the last selected playlist publishes a valid empty watch library. Reconciliation requires a matching source identity and complete playlist membership and hierarchy; failed saves, incomplete inventories and data belonging to another account preserve the selection and saved watch content. A valid reconciliation persists even while delivery is unavailable, so relaunch can retry it. Shared files remain selected, and obsolete files used by playback are collected after playback releases them.

Application context carries a versioned head: publisher UUID, increasing revision, opaque library identity, selected playlist IDs, publication readiness and refresh failure status. The complete library travels through `WCSession.transferFile`, using the existing library protobuf inside a JSON envelope. Each queued file is immutable and stays on disk while the system has it outstanding. Publication state persists before enqueueing; activation and failed-transfer callbacks retry the latest publication. Metadata is queued before its music and artwork, so bulk content does not get enqueued ahead of the snapshot needed for browsing. If metadata delivery cannot be queued, content publication waits for a successful retry. No live `sendMessage` round trip is required. Opening the watch can also queue a durable refresh request through user info.

The watch stages received files synchronously before the connectivity delegate returns. Its inbox survives process recreation and accepts files before their context arrives. A single database writer serializes control changes and imports. Track rows, playlist rows, accepted revision and desired file identities commit together. Invalid graphs, unsafe filenames, corrupt data and failed saves preserve the last committed library. Relaunch retries valid interrupted imports. Files and contexts from older revisions cannot undo a newer selection; retired publisher UUIDs cannot regain control.

A new library/account or sign-out advances the control revision and rejects old incoming files. As with phone sign-out, saved metadata and local music remain available until a valid replacement arrives. Normal token refresh preserves the identity and accepted revision. Never configured, waiting for the phone, a successfully saved empty selection, and failed refresh are distinct states. Saved content remains browsable during refresh failure, independently of phone reachability.

Receiving services start in the watch app initializer, before a scene is needed. Connectivity background tasks are held until session activation, system pending content and queued import work permit completion. Unit tests verify this lifetime boundary and inbox recovery; they do not establish background throughput on paired hardware.

The production watch composition (`WatchLibraryServices`, used by `WarehouseWatchApp`) contains local stores, a downloaded-only player, local artwork reads and paired-phone metadata/content receivers. It has no server sync, HTTP fallback, playback/deep prefetch or manual preparation service. The watch target excludes the phone metadata sync and publication services; shared phone player/networking functionality stays available to its existing callers. Application context contains only the versioned library head, with no server URL or bearer token. Phone token refresh preserves the opaque library namespace and downloaded content.

The watch player coordinates phone playback at the shared start/resume boundary. Track selection, Play/Shuffle, local Now Playing and system transport controls pause a reachable phone that reports play intent before starting local audio. Pausing the watch, seeking without starting playback and duplicate playback observations do not send a handoff. An unavailable phone never blocks downloaded playback. The phone player has no handoff callback.

Old credential/configuration fields are discarded on watch launch. The old offline selection manifest is read only to restore retention; it cannot start transfers or change selection. It is retired only after new phone intent is durable. Historic diagnostic reply values and saved metadata protocol guards remain readable until final migration cleanup. Legacy file requests receive an unavailable reply, and incoming legacy files are ignored. Old or unsupported contexts report refresh failure while preserving saved local content, with no HTTP fallback.

Validation uses temporary Core Data stores and a controllable transport, including a 500-track round trip, valid empty selection, old-store migration, local edits, failed phone loads, corrupt receipts, interrupted saves, duplicate/out-of-order revisions, account changes, publisher replacement and background initialization. Run `rake ios:test`, `rake ios:build`, `rake checks` and the configured `prek` hooks. Physical bulk and lifecycle evidence remain in wh-8l1.4 and wh-8l1.9.

The phone content queue persists every desired music and artwork identity, deduplicating shared filenames within each type. It permits at most four content transfers or outstanding receipt waits, independent of foreground reachability. Before enqueueing, it creates an immutable private source copy and persists the file descriptor (publisher, library, revision, type, name, byte count and SHA-256 digest). Ordinary phone sync can remove its original without interrupting the transfer. Private copies remain while the system owns them, even after deselection; terminal copies are collected when the system relinquishes them.

The watch synchronously stages an incoming descriptor and its bytes as one inbox directory before returning from the file delegate. Staging checks the declared size and available space, preserving a 32 MB reserve. Metadata controls are the authority: a file preceding its snapshot waits; an old revision, changed account, unselected filename or mismatched type cannot commit. A new context pauses commits while its database write is pending. The receiver protects selected music and artwork from eviction, verifies byte count and digest, and applies the existing cache admission policy before a same-volume file commit. Artwork and music have independent delivery states; missing artwork never gates downloaded music playback.

A durable receipt records verified watch storage. System transfer completion only changes the phone job to awaiting receipt. Durable user-info queries and replies repair lost acknowledgments from the watch ledger and verified files; they do not require a live message reply. If the phone stops between persisting and enqueueing, a query establishes whether a retry is needed. If the watch stops after file commit but before receipt persistence, its staged manifest recognizes the committed bytes on recreation and repairs the receipt. Duplicate deliveries and receipts do not count twice. Transfer delays have no two- or thirty-second cancellation deadline.

The watch receipt ledger retains the latest result for each selected file in the accepted metadata head, plus exact retry results for that head's staged transfer manifests. Validated, durably retained replacement selections prune old revisions, deselected files and replaced publisher/library identities. Pending or failed metadata preserves the previous ledger. Compaction saves atomically before changing in-memory evidence; staged bytes remain available if that save fails. Once a manifest is consumed, superseded results leave the ledger. A query for a pruned transfer can recover delivery only when its descriptor still matches current selection authority and its bytes pass size and SHA-256 verification. This bounds historical receipt storage by the selected inventory and recoverable staged work, rather than installation age.

Metadata inbox cleanup uses the database's durable retired-publisher authority, removing late snapshots from retired publishers even when they claim a higher revision. Old revisions and conflicting identities at the current publisher revision are also removed. Unknown publishers and future revisions remain staged until their application context arrives; no age limit or arbitrary file cap can safely declare those files obsolete. Storage for unresolved future contexts therefore follows pending work, while ordinary selection/revision/publisher churn leaves no obsolete snapshot history. `WatchJournalRetentionTests` covers repeated churn, interrupted compaction and import, restart recovery, lost receipts and a 10,000-entry legacy ledger, reporting simulator ledger size and startup/compaction/write times without claiming watch hardware performance.

Transient failures and Storage Full retry automatically with exponential backoff, from 10 seconds to a capped interval of one hour for actual transfer or commit attempts, whenever execution and transport permit. Awaiting receipt queries run no more often than once a minute and are deduplicated against outstanding system user info. A due retry blocked by occupied slots waits for completion or a later wakeup instead of spinning. Permanent file failures remain in the persisted status and release the slot for unrelated content. Missing phone files remain pending and are rechecked on eligible wakeups. No content queue or receiver uses watch HTTP. Activation, selection/publication changes, file completion, user-info receipt and foreground return replenish the phone queue. Watch background launch initializes the receiver and holds connectivity tasks through metadata import, delegate staging and asynchronous content processing.

Bulk copying and SHA-256 verification run on a separate serial `WatchContentWorker` actor for each queue or receiver. Phone preparation reserves one of the four transfer slots before yielding; preparing copies and recovery sources remain pinned until that worker exits, including cancellation. The worker fingerprints its private copy. Selection or namespace changes cancel preparation, and the main actor rechecks the exact head, generation, job and transport availability before persisting the descriptor/job and enqueueing without another suspension. Damaged-journal descriptors are recovery candidates rather than proof of valid bytes; the worker verifies them before reuse.

The watch serializes inbox commits, receipt queries and staging failures in one asynchronous runner. It rechecks selection generation and authority after each worker await, then checks the verified file's inode, size and modification time before a receipt or rename. Cache admission, active-playback protection, the same-volume commit and durable receipts remain serialized on the main actor. A new context pauses old commits immediately. Delegate staging still persists the manifest and bytes synchronously before returning; hashing happens later. Pending worker work registers synchronously with `WatchPhoneSession` background lifetime and releases only after processing and receipt persistence finish, even when the system reports no remaining content.

`WatchContentWorkerTests` sets a simulator responsiveness budget of 100 ms for command dispatch while preparing/verifying four 64 MiB music files in a 300-track library, and while draining the remaining selected files. `rake ios:test` disables test parallelism across the full unit target: a suite's `.serialized` trait only serializes its own tests, allowing unrelated fixtures to occupy the same main actor and distort command timing. The profile still runs real content workers concurrently with playback commands, and the 100 ms limit remains unchanged. Controlled worker gates test head replacement, cancellation, unavailable transport, source removal after enqueue and background completion. This is simulator evidence; it does not establish physical watch latency, watchdog behavior or delivery throughput.

Phone selections also own watch retention and cleanup. A validated snapshot matching the accepted head persists its music and artwork inventory in `watch-selection.json` before releasing legacy retention or deleting any files. Missing, stale or unreadable snapshots preserve existing downloads; a valid empty selection deliberately removes them. Relaunch restores retention synchronously before eviction. If the retention record is unreadable, existing files remain protected until a valid snapshot repairs it. The read-only legacy offline selection manifest is retired only after the new intent is durable. Failed persistence keeps the old intent and files, blocks premature content commits and retries on the next eligible receiver wakeup.

Updated snapshots reconcile additions, playlist deletion, deselection and changed filenames. Shared files remain while any selected playlist references them. Obsolete files are removed immediately unless playback still uses them; player protection covers the current music, queued next music and displayed artwork. Releasing that protection collects obsolete files without another selection action. Changed bytes under an active filename wait in the durable inbox until playback releases that file, then commit automatically. Valid existing files are verified against incoming descriptors and reused without rewriting them. Selected files can exceed the old opportunistic cache budget, but actual disk capacity, staged bytes and concurrent reservations still govern admission. Reservations are transient commit claims; recreation drops them and rebuilds admission from the durable inbox and actual free space. Storage Full preserves downloaded selected music and pending phone jobs, which retry with backoff when capacity and execution permit.

`WatchContentDeliveryTests` covers 300 cached music files plus artwork through bounded queues, shared identities, repeated queue/receiver recreation, production selection and session receipt dispatch, synchronous staging, files preceding snapshots, lost acknowledgments, source cleanup, interrupted file and receipt commits, deselection and account changes, corruption, storage admission and backoff. It also covers authoritative retention before eviction, mirrored membership and filenames, active local playback during library replacement, valid empty selection, migration persistence failure, download reuse, and reservation recovery. This controlled pipeline establishes correctness; physical background timing remains in wh-8l1.4. Missing phone files wait for normal phone sync; physical lifecycle validation remains in wh-8l1.9.

The phone Apple Watch settings screen is the sole playlist selection surface. Selecting requests and retains music and artwork automatically, with no watch preparation step. It preserves the existing leaf-playlist and folder grouping. Streaming, Fill Ahead, watch Server URL and Offline Playlists/Prepare controls are absent. Phone remote controls, downloaded-only playback and diagnostics remain available. Empty selections explain how to choose playlists on iPhone; pending or failed refreshes preserve the saved library for browsing and playback. Local Now Playing remains reachable whenever the player has a current track, including a paused queue, independently of empty or failed library loading and phone remote availability. Playback continues to protect only the files it actually uses; opening the controls does not retain deselected files.

Phone remote controls update optimistically, then accept the matching command reply or a phone state push. A failed or malformed reply can follow a command that already changed the phone, so the watch reconciles with state queries without resending the command. Each refresh allows three queries, with one- and two-second delays before retries. New commands, phone state pushes and disconnection cancel obsolete queries and fence their late replies. Exhausting retries displays Retry iPhone State; foreground entry, reconnection or that button starts a fresh refresh. Reachability alone does not confirm a command. `WatchPhoneSessionTests` covers delivery failures, applied commands with lost replies, malformed replies, bounded retries and newer commands during reconciliation through the production session boundary.

`WatchLibraryProgress` is the shared production presentation boundary. The phone queue persists the selected snapshot with its jobs so aggregate and per-playlist downloaded/total music counts survive restart and disconnection. A verified watch receipt or manual inventory verification advances phone counts; phone cache hits, enqueues and system completions do not. Shared files count once in the overall track inventory and appear in each playlist that needs them. Ready requires all music in the displayed selection; artwork has separate counts and failures.

A normal phone sync can publish a new metadata revision when only a play count or rating changes. The phone preserves acknowledged music and artwork across forward revisions from the same publisher and library, matching the export's content-addressed filenames by file type. The new inventory removes obsolete identities and introduces new files as pending. Original receipt descriptors remain the evidence for retained downloads; unacknowledged transfers are recreated for the new revision, and late receipts for those obsolete transfers cannot advance progress. A pending refresh keeps the last inventory and acknowledged counts until its validated snapshot arrives. Playlist selection changes pause obsolete transfers while preserving acknowledged music and artwork until the new inventory arrives; that inventory retains shared files and removes deselected identities. Account changes, publisher changes, sign-out and clearing the selection clear the previous evidence.

Automatic watch inventory reconciliation checks those retained acknowledgments against actual storage at most once every rolling 24 hours. Phone activation/foreground entry, reachable reconnection, watch activation/foreground library requests and metadata publication check eligibility or resume an unfinished challenge. Ordinary sync uses the phone's durable file receipts to skip already delivered files; a play-count, rating or metadata revision does not force another scan or resend unchanged acknowledged content. The phone persists the first enqueue time, preserving the daily limit across relaunch, revisions and configuration invalidation. An offline challenge consumes the budget only when first sent. Eligibility does not create a background wakeup or guarantee a scan at a particular time.

An automatic challenge carries a fresh UUID and the exact selected metadata head; the phone marks only jobs already acknowledged when it starts. The watch persists requests received before matching metadata is ready and answers only after a validated snapshot and retention intent have been accepted. It saves the complete scan before sending any response and replays that capture on retries, including after relaunch. A separate persisted watch-side 24-hour limit prevents delayed requests from producing scans close together. A new revision cancels an obsolete challenge without resetting the daily budget. A reinstalled watch receives metadata again, but missing-file detection and repair may wait until the next eligible daily check; ordinary sync does not bypass the limit.

Each durable user-info response contains at most 64 explicit type/name/size entries; absent or empty files carry no size. Missing batches never imply missing files. The phone persists each batch's progress, ignores duplicate entries and obsolete challenges, and retries incomplete challenges at most once a minute when execution and connectivity permit. These retries reuse the existing watch capture, rather than scanning again. Only missing or differently sized acknowledged files lose delivered status. Their repair starts with a fresh transfer identity, so late old receipts cannot restore an invalid acknowledgment. Files acknowledged after the challenge began are unaffected by its older observations. Account, publisher and revision changes fence out earlier responses.

Automatic inventory is a presence and size check of the export's content-addressed filenames, not a full disk-integrity scan. It cannot promote an unverified file to delivered or detect same-size corruption; content admission and receipt recovery retain SHA-256 verification. Present acknowledged files need no retransmission, while missing phone sources wait for normal sync and Storage Full uses the existing delivery retry policy. Watch transport unavailability and filesystem errors preserve pending requests rather than reporting an empty library. Damaged saved challenge state is logged and discarded without disabling the content receiver; phone retries reconstruct it. Lifecycle checks repair later storage loss; reconciliation does not guarantee immediate convergence while either device is unavailable. `WatchInventoryTests` covers loss of music/artwork, complete watch data loss, partial/reordered/duplicate batches, relaunch, revision and namespace fencing, delayed receipts, transport interruption, source/storage waits, payload validation and diagnostics.

The watch Downloads section offers **Sync Downloaded Status**. It saves a manual request before enqueueing it and shows pending feedback until the phone confirms durable reconciliation. Verification or storage failures offer retry feedback; changing the library fails the old action while preserving playable files. Disconnection leaves the action pending, with lifecycle and minute-spaced retries whenever execution permits.

Manual requests carry the exact accepted head, UUID and a persisted increasing sequence. The phone fences reordered requests and targets all selected jobs, including music and artwork without previous receipts. The watch fingerprints selected files on its serial content worker and persists one complete capture before sending at most 64 entries per report. Replies replay that capture across interruptions instead of repeating the scan. Missing entries never imply missing files. The phone compares size and SHA-256 with its authorized descriptor or stable local source; an unavailable source cannot authorize an unknown file. Matching bytes establish durable delivery without copying or transferring content. Invalid prior claims receive fresh repair identities; inventory never deletes watch playback files. New delivery receipts supersede outstanding checks, and file completion cannot undo verified inventory status.

Manual scans bypass the automatic daily cooldown. Automatic presence/size scans remain limited to one per rolling 24 hours; manual captures may defer the next automatic watch scan. Completion acknowledges reconciliation, including missing files awaiting normal delivery, rather than claiming every selection is ready. No physical-device timing or background completion guarantee is implied.

The watch derives counts from files actually present in its selected library, including retained downloads usable before a new acknowledgment. The phone also sends coalesced, durable user-info preparation reports for missing phone files, storage waits and permanent failures. Reports carry the exact metadata head and a persisted increasing sequence, with aggregate and per-playlist state. The watch saves a bounded history so reports can precede metadata; duplicate, older and mismatched reports cannot advance local counts or replace newer state. A report never establishes a downloaded file. Missing phone files explain that normal phone sync is needed. Storage Full offers freeing space or deselecting playlists while preserving downloaded playback. The phone identifies its displayed counts as the last reported watch status while disconnected.

Watch startup shows loading while restoring the saved configuration, rather than offering setup before that configuration is known. Phone context updates pause content commits while metadata is reconciled, but retain the last accepted download status and counts for display. Incidental content resumes cannot authorize paused commits; metadata reconciliation does that. An unchanged context preserves progress, while an accepted unconfigured phone head still offers setup. `WatchLibraryServicesTests` covers these presentation transitions, and `WatchContentWorkerTests` verifies that paused verification cannot commit or acknowledge files until reconciliation.

Progress tests exercise delayed and duplicate acknowledgment, queue/receiver restart, unavailable delivery, missing phone files, storage receipts preceding system completion, permanent failure, independent artwork failure, empty selection, stale preparation reports and pending/failed metadata refresh. The companion UI test verifies selection and progress without exposing the obsolete controls. Final watch UI and paired-device behavior remain part of wh-8l1.9.

Delivery startup has a separate, retryable status on each device. A temporary read or write failure leaves the saved state intact and shows Delivery unavailable, while saved music remains browsable and playable. Normal phone publication and watch launch retry initialization; Retry Delivery on either device also recovers malformed delivery journals without reinstalling. Recovery copies the damaged bytes to a private `recovery/` archive before atomically replacing the journal. If either write fails, the original remains available for a later retry. Selection stays in phone settings and the watch's database/cache retention records; none is rebuilt from a damaged delivery journal.

A damaged phone publisher receives a new persisted publisher UUID and republishes from the authoritative, source-matching phone database. The watch retires the previous publisher when that context arrives, fencing late old contexts, snapshots, content and receipts. System-owned metadata and private source files remain on disk until their transfers finish. Each private content copy has an independent immutable descriptor; startup also creates descriptors for older known copies. Queue recovery verifies these descriptors and bytes, then waits for a validated selected snapshot before restoring work. Exact-head jobs query for receipts first; replacement-head jobs reuse the verified same-library, content-addressed source under a fresh transfer identity. Recovery never promotes files to delivered. Legacy copies with no surviving descriptor remain protected as unidentified sources; their filename and account cannot safely be guessed, so missing selected originals still need normal phone sync.

A damaged watch receipt journal rebuilds from the committed metadata, durable staged manifests and verified local bytes. Recovery preserves both downloaded music and the staged inbox. Existing files remain playable; only current-authority size/SHA-256 verification can generate a replacement receipt. Startup errors are independent of metadata refresh errors, so content recovery does not hide a failed or unsupported metadata context. Each device surfaces that delivery recovered. `WatchDeliveryRecoveryTests` covers temporary read/write failures, failed archival/replacement, original phone file cleanup, outstanding transfer ownership, publisher replacement, lost receipts, staged watch recovery and relaunch. Recovery archives and unidentified legacy sources are retained for diagnosis rather than deleted by age.

`WatchLibraryServicesTests` records server requests across production launch, browsing, local playback, missing artwork, refresh, retry, storage recovery and relaunch. These tests also cover obsolete/unsupported peer contexts and damaged content-ledger startup while saved playback remains available.

Watch play reports retain their event UUID, track ID and play source identity in `plays.json` until a matching durable phone receipt arrives. System enqueue and successful transfer completion do not remove a play. Terminal transfer errors, lost receipts and relaunch retry the same event; retries wait at least a minute during normal execution and skip outstanding system transfers. Activation and foreground return also check pending plays. A failed watch save prevents enqueue; a failed receipt-removal save preserves the pending event for a safe retry.

The phone receives plays during app initialization, independently of a scene. It atomically saves the pending update and an event-ID/track-ID/source-identity ownership record in `updates.json` before enqueueing the receipt. Failed saves roll back ownership and withhold the receipt. Repeated delivery acknowledges the existing event without appending another update, including after restart or successful downstream removal. Ownership records persist for the installation lifetime because an old watch retry can arrive after an arbitrarily long disconnection. Existing pending-array files migrate on their next save. Servers that disable user-change tracking durably consume the event and remove its eligible pending update without sending an HTTP request, matching the existing phone policy. The HTTP update contract is unchanged; these receipts establish exactly one durable phone update, not server-side idempotency for an HTTP request whose response is lost.

Song reads serialize with library imports and copy ownership from the committed phone library or accepted watch snapshot. A newer control head cannot relabel retained metadata. Queue rows, inserted/history tracks and restored snapshots preserve this identity; a restored row cannot resolve a colliding track ID from a different library. A protected old track finishing after replacement reports its original identity. Receipts must match the complete event, including its source. Ordinary same-account token refresh preserves the identity.

Phone plays, edits and artwork uploads persist their source identity alongside each pending update. Sending requires a matching server/account identity and a saved export policy belonging to that identity; sign-out pauses sending. Configuration is checked again after each asynchronous request. Updates from older libraries remain on disk, do not block current-library updates, and resume only after the matching account is configured and its export policy is available. They never retain credentials. A server that disables changes consumes only its own eligible updates. Unknown-source reports and legacy pending updates remain durably unassigned: there is no reliable evidence to attach them automatically to a current account. Legacy ownership records still acknowledge identical unassigned retries, preserving the existing receipt contract. No age-based deletion or automatic reassignment is performed. HTTP retry idempotency remains tracked separately in wh-2wn.13.
