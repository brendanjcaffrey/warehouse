# Paired watch library diagnostic capture

Warehouse supplies watch metadata, music and artwork exclusively through the paired phone. Watch playback uses downloaded music. Phone playlist selection starts durable delivery whenever the system permits; selection, system transfer completion and watch readiness are separate states. Normal phone sync supplies missing phone files. Physical background throughput remains a measurement in wh-8l1.4; an old report containing only system events does not establish a delivery failure.

## Capture and share

1. Install the same current build on both peers. Record models, OS versions, music codec/bitrate, playlist track count and approximate bytes, connectivity, charging state and whether each app is foreground, background or locked. The exports include build version/number, simulator status, model and OS. Keep clocks synchronized.
2. Save any previous captures. On the watch open **Diagnostics → Start New Capture**. Phone totals have their own capture start time and survive relaunch. Save a phone baseline using **Settings → Apple Watch → Diagnostics → Save iPhone Capture**; compare start/end totals when phone and watch capture windows differ.
3. Select at least five representative tracks in the phone's watch playlist settings, or a realistic bulk playlist for an overnight observation. Record existing downloaded counts and selection time. Delivery does not require playback, charging or leaving the watch app open. Missing music stays dimmed and untappable. Do not reinstall or clear app data during a run.
4. At the end, on the watch refresh Diagnostics and **Send to iPhone**. Sending uses a live data message and needs a reachable phone. A success means both a watch report and a phone report taken at receipt time were saved. Their `pairID` matches. Share both from the phone's Apple Watch Diagnostics list. Sending failure leaves the watch capture intact. A phone capture can also be saved independently while disconnected.
5. Keep observations alongside the exports. Record elapsed time, delivered count/bytes deltas and device state changes. Existing partial physical observations remain useful; the event ring need not contain every event from an overnight run.

## Read the exports

`delivery` is sampled at export time, independently of the event ring. Match `head` and `inventoryHead` using opaque publisher/library identifiers and revision. A pending metadata head can differ from the retained inventory head. Music and artwork each expose desired, delivered, pending and failed counts and known bytes, plus status counts. `unknownBytes` counts files whose size is unavailable; zero known bytes does not mean zero intended bytes. Phone delivered state comes from durable watch receipts; watch delivered state comes from actual selected files on disk. Watch `localMusic`/`localArtwork` include the entire local inventory, including obsolete files protected by playback. Free capacity, staged inbox count, phone system outstanding count, receipt waits, transport availability and next attempt time help explain pending work.

`totals` preserves cumulative event counts, bytes and first/last timestamps across ring truncation and relaunch. Keys combine event and file type (or `metadata`). Enqueue, system completion and staging bytes count attempts, including retries. `contentCommitted` counts new verified cache commits; `contentReused` counts already verified files. These two outcomes share an identity ledger, so recovery after a commit with failed receipt persistence cannot add reuse bytes for that transfer. `phoneAcknowledged` counts each accepted delivered receipt identity once. `receiptSent` means the persisted receipt was handed to the send adapter, not that the phone received it. Receipt persistence, send/replay and query totals count control events and carry zero aggregate content bytes. Do not sum phases as delivered bytes. Different revisions can legitimately deliver the same content again. Totals cover the capture window, not time before instrumentation or before app data was cleared.

The last 512 `events` provide transition detail with timestamps, opaque transfer ID, publisher/library namespace and revision, file type, bytes, status and classified errors. The same transfer ID joins both peers. `metadataPublished`/`metadataAccepted` identify publication and accepted import; `metadataCompleted` means system completion only. `contentEnqueued` → `contentCompleted` → `contentStaged` → `contentCommitted` or `contentReused` → `receiptPersisted`/`receiptSent` → `phoneAcknowledged` separates scheduling, local verification and acknowledgment. `receiptQuery` repairs lost acknowledgments. `contentTransferFailed` records a system file-transfer error independently of terminal job failure. `contentRetry`, `contentStorageFull`, `contentFailed` and `queueWakeup` explain wakeups and errors. Metadata/file delivery can arrive out of order. Legacy `phoneDelivered`/`phoneFailed` events describe the old transport and must not be used to measure the current pipeline.

`inventoryRequested` records a phone challenge attempt, `inventoryScanned` a fresh watch storage scan persisted for replay, and `inventoryReported` a bounded watch response handed to the durable transport. Their event IDs match the challenge UUID. A retry can produce more requests and reports without another scan; fresh scans are limited to one per rolling 24 hours. `inventoryConfirmed` records an acknowledged file still present at its expected size; `inventoryMissing` records an absent or differently sized file whose old acknowledgment was revoked. Those events use the original transfer ID and the current challenge head, which can have a newer revision than the receipt. Repairs then use fresh IDs and the usual content/receipt events. `inventoryCompleted` means every targeted acknowledgment has been checked, not that missing files have finished redelivering. `inventoryRejected` identifies obsolete or invalid responses; `inventoryFailed` identifies a watch inventory processing/storage error. Inventory event totals are control counts and contribute zero transferred bytes; confirmations must not be added to verified-delivery totals.

The phone's sampled `delivery.inventoryPending` counts acknowledgments awaiting inventory responses, `inventoryRequestID` identifies the active challenge, and `inventoryCompletedAt` is its last completed check time for the current state. `inventoryStartedAt` records the phone's last first-enqueue time, while `inventoryEligibleAt` shows when another new challenge is allowed; both survive metadata/configuration changes. On the watch, `inventoryPending` counts requests waiting for matching metadata, transport or scan eligibility, and `inventoryRequestID` identifies the first such request. Watch `inventoryStartedAt` is the actual persisted scan time and `inventoryEligibleAt` is its next allowed fresh scan time. `nextAttemptAt` on the phone includes inventory retries, which are independent of the daily cooldown. Eligibility is not a scheduled wakeup. A completed inventory can lower delivered counts and expose repair work even while cumulative historical delivery totals remain unchanged. Presence/size reconciliation does not scan for same-size corruption or prove physical background throughput. Inventory exports contain no filenames, content digests or credentials.

`capture` contains the capture ID/start, `totalsStartedAt` for cumulative instrumentation coverage, total event count, ring capacity and dropped event count. `persistenceFailed` reports a diagnostic write failure; it makes relaunch continuity uncertain. Long-run totals do not derive from the ring. Upgrading preserves legacy events while starting cumulative coverage at the upgrade; do not infer throughput for the earlier interval. Reports created before this instrumentation lack these fields and cannot establish current-protocol throughput. The private identity ledger is stored locally and excluded from the export. Tokens, URLs, filenames, playlist names, content digests and error descriptions are excluded; arbitrary error domains become `other`.

## Device observations

Measure a nearby phone in foreground, background and locked states with watch foreground and wrist down, charging and off charger. Include reconnection, app relaunch with outstanding files, and downloaded playback without the phone. Storage pressure must preserve selected downloaded music while missing files remain pending; record free bytes and Storage Full. Compare the phone's receipt waits with watch inventory to distinguish delayed acknowledgments from delayed bytes. Playback startup/stall events remain useful for downloaded playback; verify audible output physically.

For the connectivity background-completion race (wh-2wn.4, lifecycle validation wh-8l1.9), use a debug build to trace the final application-context, metadata-file, delivery-report and receipt-query callbacks separately with the watch inactive. Record callback entry, synchronous file staging, `hasContentPending` becoming false, `contentActivity.count`, `library.pendingOperations`, persistence/response completion and `setTaskCompletedWithSnapshot(false)`. Background completion must follow deferred processing and any asynchronous metadata import, even when the system has already delivered its last callback. Include overlapping callbacks, a failed metadata save and a failed report/receipt write; completion must release after failure handling, and a staged snapshot awaiting a retry must survive relaunch. Keep any deliberate debugger delays and injected failures explicit in the run notes. Unit tests delay actor work deterministically; device traces establish only the scheduling actually observed on the recorded build. Previous lifecycle captures do not validate this new race regression.

For downloaded playback activation (wh-2wn.6), install the build containing the fix on the watch and confirm the chosen music is downloaded. Disconnect the phone so playback cannot come from it. With Bluetooth headphones initially disconnected, tap a downloaded track once and select the headphones when watchOS requests an output. Record audible playback starting without another Play tap, the playhead advancing, and the number of attempts. Repeat after relaunch by resuming the saved queue at a nonzero position. During a separate output-selection attempt, tap Pause before activation completes: connecting headphones must leave playback paused until an explicit Play. Also decline output selection and verify a later Play can recover, and skip while activation is pending to verify only the new track starts. After audible playback begins, trigger a real interruption or disconnect the headphones and verify playback pauses. Record watch model, OS, build, headphone model, route-selection/interruption timing and each result on wh-2wn.6; simulator regressions alone do not satisfy its physical Bluetooth acceptance criterion.
