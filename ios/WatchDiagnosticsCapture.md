# Paired watch library diagnostic capture

Warehouse supplies watch metadata, music and artwork exclusively through the paired phone. Watch playback uses downloaded music. Phone playlist selection starts durable delivery whenever the system permits; selection, system transfer completion and watch readiness are separate states. Normal phone sync supplies missing phone files. Physical background throughput remains a measurement in wh-8l1.4; an old report containing only system events does not establish a delivery failure.

## Capture and share

1. Install the same current build on both peers. Record models, OS versions, music codec/bitrate, playlist track count and approximate bytes, connectivity, charging state and whether each app is foreground, background or locked. The exports include build version/number, simulator status, model and OS. Keep clocks synchronized.
2. Save any previous captures. On the watch open **Diagnostics → Start New Capture**. Phone totals have their own capture start time and survive relaunch. Save a phone baseline using **Settings → Apple Watch → Diagnostics → Save iPhone Capture**; compare start/end totals when phone and watch capture windows differ.
3. Select at least five representative tracks in the phone's watch playlist settings, or a realistic bulk playlist for an overnight observation. Record existing downloaded counts and selection time. Delivery does not require playback, charging or leaving the watch app open. Missing music stays dimmed and untappable. Do not reinstall or clear app data during a run.
4. At the end, on the watch refresh Diagnostics and **Send to iPhone**. Sending uses a live data message and needs a reachable phone. A success means both a watch report and a phone report taken at receipt time were saved. Their `pairID` matches. Share both from the phone's Apple Watch Diagnostics list. Sending failure leaves the watch capture intact. A phone capture can also be saved independently while disconnected.
5. Keep observations alongside the exports. Record elapsed time, delivered count/bytes deltas and device state changes. Existing partial physical observations remain useful; the event ring need not contain every event from an overnight run.

## Read the exports

`delivery` is sampled at export time, independently of the event ring. Match `head` and `inventoryHead` using opaque publisher/library identifiers and revision. A pending metadata head can differ from the retained inventory head. Music and artwork each expose desired, delivered, pending and failed counts and known bytes, plus status counts. `unknownBytes` counts files whose size is unavailable; zero known bytes does not mean zero intended bytes. Phone delivered state comes from durable watch receipts and manual inventory verification; watch delivered state comes from actual selected files on disk. Watch `localMusic`/`localArtwork` include the entire local inventory, including obsolete files protected by playback. Free capacity, staged inbox count, phone system outstanding count, receipt waits, transport availability and next attempt time help explain pending work.

`totals` preserves cumulative event counts, bytes and first/last timestamps across ring truncation and relaunch. Keys combine event and file type (or `metadata`). Enqueue, system completion and staging bytes count attempts, including retries. `contentCommitted` counts new verified cache commits; `contentReused` counts already verified files. These two outcomes share an identity ledger, so recovery after a commit with failed receipt persistence cannot add reuse bytes for that transfer. `phoneAcknowledged` counts each accepted delivered receipt identity once. `receiptSent` means the persisted receipt was handed to the send adapter, not that the phone received it. Receipt persistence, send/replay and query totals count control events and carry zero aggregate content bytes. Do not sum phases as delivered bytes. Different revisions can legitimately deliver the same content again. Totals cover the capture window, not time before instrumentation or before app data was cleared.

The last 4,096 `events` provide transition detail with timestamps, opaque transfer ID, publisher/library namespace and revision, file type, bytes, status and classified errors. The same transfer ID joins both peers. `metadataPublished`/`metadataAccepted` identify publication and accepted import; `metadataCompleted` means system completion only. `contentEnqueued` → `contentCompleted` → `contentStaged` → `contentCommitted` or `contentReused` → `receiptPersisted`/`receiptSent` → `phoneAcknowledged` separates scheduling, local verification and acknowledgment. `receiptQuery` repairs lost acknowledgments. `contentTransferFailed` records a system file-transfer error independently of terminal job failure. `contentRetry`, `contentStorageFull`, `contentFailed` and `queueWakeup` explain wakeups and errors. Metadata/file delivery can arrive out of order. Legacy `phoneDelivered`/`phoneFailed` events describe the old transport and must not be used to measure the current pipeline.

`delivery.outstandingTransfers` and `receiptTransfers` expose each phone-owned transfer's opaque `id`, namespace, type, size, `startedAt` and `ageSeconds`. The phone timestamp is the last durably saved enqueue intent, immediately before handing the file to WatchConnectivity; it is not the system's actual start time. Dates survive queue relaunch, and retries update the enqueue time. Older jobs and recovered descriptors can have no timestamp or age; omitted fields mean unknown, not zero. `preparingFiles` counts copies or hashes that have not yet reached enqueue. Outstanding transfers can fill all four slots even when there are no receipt waits. A free slot does not guarantee process execution or system delivery.

On the watch, `stagedTransfers` identifies inbox files with their directory creation timestamp and age, which survive relaunch. Each entry's `authorized` flag says whether current selection and metadata permit that descriptor to commit. `processing` reports `paused`, current selection authorization, pending operation count, requested drain/progress scan, queued queries, and the active phase/file ID with its phase start time. Phases distinguish draining, receipt queries, presence scans, existing/incoming byte verification, commit, and a file protected by playback. These describe the receiver's current operation, including time waiting for its serial worker; they do not prove the CPU is executing or directly measure hashing time. `contentProcessingChanged` preserves phase and pause/authorization transitions in the ring. Compare `contentStaged` with `contentCommitted` to find bytes that reached the watch but waited for processing.

`delivery.background` and `backgroundStateChanged` expose session activation, system content pending, library-import operations, delegate callback holds, receiver/inventory operations and held connectivity background tasks. Repeated identical background states are suppressed. `backgroundCompleted` records the number of completion callbacks released in `completedTasks` and the remaining state. It is persisted before invoking those callbacks so the trace does not depend on execution continuing after the final system task completes. A held task records an application lifetime hold, not a guarantee of continued execution. A staged file plus a long-running processing phase points to watch processing; four outstanding phone transfers with no watch staging point to system delivery. Capture both peers before and after relaunch to preserve that distinction.

Activation receipt replay runs after the synchronous activation handler, indexes one outstanding user-info snapshot, and yields between batches of 16 saved receipts. The replay owns a counted hold before it is dispatched; `callbackOperations` includes that hold and library-request holds as well as inbound callbacks. Fresh receipts share the replay's index, with full-payload equality preserving source/status identity. Selection reconciliation and receiver replacement fence obsolete replay candidates. If transport becomes unavailable, replay releases its hold and leaves the durable ledger intact for a later activation or recovery. The per-replay index is discarded afterward so later receipt queries can retry transfers that disappeared from the system queue.

`contentCallbackReceived` is persisted synchronously at watch file callback entry, before copying bytes or scheduling main-actor work. `contentStagingCompleted` or `contentStagingFailed` marks the synchronous staging result, and `contentCallbackHandled` marks arrival at the main actor immediately before the existing `contentStaged` or failure handling. All use the original transfer ID. Staging `elapsed` measures callback entry through staging; handled `elapsed` measures the wait after the staging-result record. These use process uptime, include instrumentation and scheduling overhead, and do not measure CPU time. New callback/staging totals are control counts with zero aggregate content bytes; keep using `contentCommitted`/`contentReused` for verified delivery.

`contentQueryReceived` and `contentQueryHandled` split durable receipt-query callback entry from main-actor handling using the original transfer ID; handled `elapsed` measures that wait. Metadata file callbacks use `metadataCallbackReceived`, `metadataStagingCompleted`/`metadataStagingFailed` and `metadataCallbackHandled`, joined by a locally generated opaque callback UUID. `contextCallbackReceived` and `contextCallbackHandled` split application-context receipt from handling, joined by publisher UUID when decodable or a local UUID otherwise. A restored context read during activation does not claim a new context callback. The thread-safe capture serializes memory, journal, checkpoint, clear and report access so callback probes remain durable without requiring main-actor execution. Concurrent events appear in journal order; use their `date` fields when comparing clocks.

The report and events can contain `lifecycle`, with an opaque `processID` and the last observed `application` and `scene` states. `processStarted` records watch app initialization with a new process UUID; `applicationStateChanged` records app-delegate lifecycle notifications and `scenePhaseChanged` records SwiftUI phase changes. `unknown` means no state has been observed in this process, not foreground or background. A capture clear preserves current process/state observations, while relaunch preserves the capture history and starts a new process identity. `sessionActivationRequested` records session activation initiation, `sessionActivationCompleted` records the raw delegate completion, and the existing `activationChanged` marks main-actor handling. `backgroundTaskReceived` records entry to handling a connectivity background task alongside the current counted work. Lifecycle notifications and held tasks do not establish charging state, continuous execution or termination reason. Install the same new build on both peers before sharing these new event kinds; older captures remain readable.

Retention increased eightfold because a single bulk inventory can displace hundreds of file transitions from a 512-event ring. The 4,096-event ring remains count-bounded, and cumulative totals still survive truncation. Sharing accepts at most 4,096 events and 4,096,000 encoded bytes, using the existing 24,000-byte chunks; an oversized report fails explicitly. Update both peers before sending larger captures. The larger ring does not recover events already dropped, guarantee a complete overnight history, or establish improved throughput. Each event is synchronously appended to a bounded local journal; after 64 journal entries, an atomic checkpoint saves the ring, totals and deduplication ledger before clearing the journal. Capture IDs and sequence numbers prevent replaying checkpointed events or reviving a cleared capture after interrupted cleanup. An incomplete/corrupt journal preserves its valid prefix and marks persistence uncertain. This avoids serializing and rewriting the larger ring for every transition. Additional processing events are emitted only on state transitions.

`inventoryRequested` records a phone challenge attempt, `inventoryScanned` a fresh watch storage scan persisted for replay, and `inventoryReported` a bounded watch response handed to the durable transport. Their event IDs match the challenge UUID. A retry can produce more requests and reports without another scan; fresh automatic scans are limited to one per rolling 24 hours. `inventoryConfirmed` records an acknowledged file still present at its expected size; `inventoryMissing` records an absent or differently sized file whose old acknowledgment was revoked. Those events use the original transfer ID and the current challenge head, which can have a newer revision than the receipt. Repairs then use fresh IDs and the usual content/receipt events. `inventoryCompleted` means every targeted acknowledgment has been checked, not that missing files have finished redelivering. `inventoryRejected` identifies obsolete or invalid responses; `inventoryFailed` identifies a watch inventory processing/storage error. Inventory event totals are control counts and contribute zero transferred bytes; confirmations must not be added to verified-delivery totals.

The phone's sampled `delivery.inventoryPending` counts selected jobs awaiting inventory responses, `inventoryRequestID` identifies the active challenge, and `inventoryCompletedAt` is its last completed check time for the current state. `inventoryStartedAt` records the phone's last first-enqueue time, while `inventoryEligibleAt` shows when another new challenge is allowed; both survive metadata/configuration changes. On the watch, `inventoryPending` counts requests waiting for matching metadata, transport or scan eligibility, and `inventoryRequestID` identifies the first such request. Watch `inventoryStartedAt` is the actual persisted scan time and `inventoryEligibleAt` is its next allowed fresh scan time. `nextAttemptAt` on the phone includes inventory retries, which are independent of the daily cooldown. Eligibility is not a scheduled wakeup. A completed inventory can lower delivered counts and expose repair work even while cumulative historical delivery totals remain unchanged. Presence/size reconciliation does not scan for same-size corruption or prove physical background throughput. Inventory exports contain no filenames, content digests or credentials.

For the explicit watch **Sync Downloaded Status** action, `inventoryManualRequested` identifies phone challenge attempts and `inventoryManualScanned` identifies the persisted SHA-256 capture. `inventoryVerified` records a selected file confirmed against authorized phone bytes, including files previously pending on the phone. These events have zero transferred-byte totals and must not be added to file arrival or commit totals. Manual challenges can occur during the daily automatic cooldown; `inventoryStartedAt` on the phone continues to describe automatic first-enqueue cadence. Completion feedback means the phone durably reconciled the report, including any missing/invalid files that still need delivery. Retry reports reuse the capture; stale heads and older manual sequences cannot change current delivery state.

`capture` contains the capture ID/start, `totalsStartedAt` for cumulative instrumentation coverage, total event count, ring capacity and dropped event count. `persistenceFailed` reports a diagnostic write failure; it makes relaunch continuity uncertain. Long-run totals do not derive from the ring. Upgrading preserves legacy events while starting cumulative coverage at the upgrade; do not infer throughput for the earlier interval. Reports created before this instrumentation lack these fields and cannot establish current-protocol throughput. The private identity ledger is stored locally and excluded from the export. Tokens, URLs, filenames, playlist names, content digests and error descriptions are excluded; arbitrary error domains become `other`.

## Device observations

Measure a nearby phone in foreground, background and locked states with watch foreground and wrist down, charging and off charger. Include reconnection, app relaunch with outstanding files, and downloaded playback without the phone. Storage pressure must preserve selected downloaded music while missing files remain pending; record free bytes and Storage Full. Compare the phone's receipt waits with watch inventory to distinguish delayed acknowledgments from delayed bytes. Playback startup/stall events remain useful for downloaded playback; verify audible output physically.

For background delivery resuming only after app opening (wh-rn9), preserve a phone baseline and start a new watch capture on both updated peers. Keep the normal delivery queue intact. Record the selected/downloaded counts, device models/builds, charging, network/Bluetooth state, background app refresh setting, and any force-quit or relaunch. Launch from the device home screen without an attached debugger. First leave the watch app open long enough to establish a foreground comparison, then leave both devices charging nearby with the watch app inactive and the phone locked. Before opening the watch at the end, save another phone capture to preserve outstanding transfer/receipt ages. Record the exact time the watch leaves the charger and the app opens, then send the paired capture. Do not reinstall or clear app data during the run. Optional Console/platform logs should cover both the inactive interval and opening; record their availability rather than treating absent logs as absent callbacks.

Apple describes connectivity background tasks as delivery opportunities that must remain held until session activation, pending delivery and app processing finish ([background tasks](https://developer.apple.com/documentation/watchkit/wkwatchconnectivityrefreshbackgroundtask), [pending content](https://developer.apple.com/documentation/watchconnectivity/wcsession/hascontentpending)). The 2026-10-14 updated capture places four artwork files in the watch inbox at 01:20/01:37, still uncommitted at the 08:00 phone baseline and committed at 08:19 after app opening. Raw query callbacks also arrive while main-actor handling does not progress. A production-activation regression reproduces synchronous receipt replay blocking incoming callbacks: 1,000 saved receipts caused 1,002 queue reads and about 5.6 seconds of simulator delay. Indexing alone reduced reads to three but still blocked callback handling until replay ended; incremental replay lets incoming callbacks run before it drains. These local results identify and remove a reproducible bottleneck, not the exact cause of every recorded suspension or initialization. Repeat the physical procedure after installing the replay change; compare raw arrival, actor handling, commit and background completion without assuming that all selected files finish overnight.

For the connectivity background-completion race (wh-2wn.4, lifecycle validation wh-8l1.9), use a debug build to trace the final application-context, metadata-file, delivery-report and receipt-query callbacks separately with the watch inactive. Record callback entry, synchronous file staging, `hasContentPending` becoming false, `contentActivity.count`, `library.pendingOperations`, persistence/response completion and `setTaskCompletedWithSnapshot(false)`. Background completion must follow deferred processing and any asynchronous metadata import, even when the system has already delivered its last callback. Include overlapping callbacks, a failed metadata save and a failed report/receipt write; completion must release after failure handling, and a staged snapshot awaiting a retry must survive relaunch. Keep any deliberate debugger delays and injected failures explicit in the run notes. Unit tests delay actor work deterministically; device traces establish only the scheduling actually observed on the recorded build. Previous lifecycle captures do not validate this new race regression.

For downloaded playback activation (wh-2wn.6), install the build containing the fix on the watch and confirm the chosen music is downloaded. Disconnect the phone so playback cannot come from it. With Bluetooth headphones initially disconnected, tap a downloaded track once and select the headphones when watchOS requests an output. Record audible playback starting without another Play tap, the playhead advancing, and the number of attempts. Repeat after relaunch by resuming the saved queue at a nonzero position. During a separate output-selection attempt, tap Pause before activation completes: connecting headphones must leave playback paused until an explicit Play. Also decline output selection and verify a later Play can recover, and skip while activation is pending to verify only the new track starts. After audible playback begins, trigger a real interruption or disconnect the headphones and verify playback pauses. Record watch model, OS, build, headphone model, route-selection/interruption timing and each result on wh-2wn.6; simulator regressions alone do not satisfy its physical Bluetooth acceptance criterion.
